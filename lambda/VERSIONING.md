# Версионирование (Hellenic Git Flow)

## Постоянные ветки

| Ветка | Роль |
|-------|------|
| `nu` | Ветка текущей разработки. Все изменения приходят сюда. |
| `omega` | Ветка стабильных релизов. Каждый коммит — тег. |

Прямые коммиты в `nu` и `omega` запрещены.

## Временные ветки

| Префикс | Назначение |
|---------|------------|
| `zeta/` | Spike, прототип, проверка гипотезы (не вливается) |
| `iota/` | Атомарная задача (feature) |
| `omicron/` | Крупная мажорная версия до первого релиза |
| `alpha/` | Внутреннее тестирование |
| `beta/` | Публичное тестирование |
| `gamma/` | Кандидат на релиз (RC) |
| `delta/` | Горячий патч (hotfix) |
| `epsilon/` | Минорное обновление |
| `lambda/` | Редактура документации |
| `tau/` | Дополнение тестов |
| `sigma/` | Дополнение логирования/метрик |

## omicron — первый шаг для нового проекта

Пока проект не выпустил ни одной версии, вся разработка идёт в
`omicron`. `nu` остаётся как «золотой снимок» шаблона после клонирования
из BaseLar.

    # Создание omicron
    git checkout nu
    git pull
    git checkout -b omicron
    git push -u origin omicron

Когда MVP готов:

1. `omicron` → `nu`.
2. Bump версии → `0.1.0`.
3. `alpha/v0.1.0` → `beta/v0.1.0` → `gamma/v0.1.0` → `omega` + тег.
4. `omicron` удаляется.

После первого релиза дальнейшая работа — через `iota/` от `nu`.

## Теги

Формат: `v<major>.<minor>.<patch>` (semver).

Тип релиза определяется номером:

| Ветка | Тип | Пример |
|-------|-----|--------|
| `gamma` | релиз | `v0.1.0` |
| `delta` | hotfix | `v0.1.1` |
| `epsilon` | минорное обновление | `v0.2.0` |
| `omicron` | мажорная версия | `v1.0.0` |

В **аннотации** тега указывается ветка, из которой пришёл релиз:

    git tag -a v0.1.1 -m "Hotfix (delta/v0.1.1). Fixed X, Y, Z."

## Правила

1. Прямые коммиты в `nu` и `omega` запрещены.
2. Каждая йота решает **одну** задачу.
3. Перед вливанием в `nu` — код-ревью и прохождение тестов.
4. Мажорный релиз: `nu` → `alpha/vX.Y.Z` → `beta/vX.Y.Z` → `gamma/vX.Y.Z` → `omega`, тег → обратно в `nu`. Все три стадии обязательны, пропуск `beta` запрещён.
5. Минорный релиз: `nu` → `epsilon/vX.Y.Z` → `omega`, тег → обратно в `nu`. Стадии `alpha`/`beta`/`gamma` не используются — минорные обновления не проходят публичное тестирование отдельно.
6. `lambda/`, `tau/`, `sigma/` — для «догоняющих» правок одной категории,
   отводятся от `nu` или `omicron`, вливаются туда же.
7. `zeta/` не вливается — код либо переезжает в `iota/`, либо удаляется.
8. `delta/` создаётся **от тега** в `omega`, не от ветки `omega`.
9. `epsilon/` создаётся от `nu`, вливается в `omega` с новым минорным тегом.
10. Каждый релиз обновляет `CHANGELOG.md` в том же коммите, что и bump
    версии. Bump и запись в changelog — атомарны: `chore: bump version
    to X.Y.Z` содержит и `__version__`, и новый раздел `## [X.Y.Z]`.

## Путь созревания кода

    zeta/_internal/  →  zeta/public/  →  epsilon/  →  beta/ или delta/
    (эксперимент)      (легаси для       (стабильный   (часть ядра)
                        отладки)          сервис)

- Код из `zeta/_internal/` не импортируется никем.
- Код из `zeta/public/` импортируем через `psi.contracts.zeta`, но
  считается временным.
- При рефакторинге — переносится в стабильный модуль или удаляется.
