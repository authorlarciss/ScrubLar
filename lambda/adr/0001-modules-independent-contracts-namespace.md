# ADR-0001: Модули независимы, контракты — namespace-классы

## Контекст

Проект строится по греческой системе. Модули (alpha, beta, gamma, delta,
epsilon, zeta, iota, sigma, mu, psi) — самодостаточные единицы со своим
функционалом. Возникает вопрос: как модули обращаются к публичным API
друг друга, не создавая связного клубка?

## Решение

1. **Модули независимы.** Иерархии зависимостей между ними нет. Каждый
   модуль решает свою задачу, не зная о деталях других.

2. **Контракт модуля — namespace-класс.** В каждом модуле есть
   `contract.py` с простым классом, объявляющим публичные имена модуля.
   Никакой логики, только объявление.

3. **Единый контракт — `nu/psi/contracts/`.** Пакет с подмодулями
   `alpha.py`, `beta.py`, `gamma.py`, ..., каждый реэкспортирует
   контракт своего модуля.

4. **Использование контрактов — только для типов.** Аннотации,
   `isinstance`, наследование. Инициализация через контракты запрещена.

5. **Инициализация — только в `psi.bootstrap`.** Создание экземпляров,
   связывание зависимостей, регистрация в `Context`.

6. **`_internal` — приватная зона модуля.** Не экспонируется в
   `contract.py`, значит недоступна извне.

7. **Правила импорта:**
   - Модуль импортирует только себя и `nu.psi.contracts`.
   - `psi.bootstrap`, `psi.application`, `psi.context` — только для
     `psi` и `main.py`.
   - `psi` не импортирует `_internal` ни одного модуля.
   - Всё проверяется `import-linter`.

## Альтернативы

1. **Прямые импорты между модулями** — быстро скатывается в связный
   клубок, тяжело менять, трудно тестировать.
2. **Единый contracts-файл** — теряется гранулярность.
3. **Полная модуляризация с внешними пакетами** — преждевременно.

## Последствия

- (+) Модули независимы, замена — локальная операция.
- (+) `_internal` защищён автоматически.
- (+) Контракт — единственное, что видно снаружи.
- (−) Дисциплина: не импортировать модули напрямую.
- (−) Чуть больше boilerplate: `contract.py`, `psi/contracts/`.
